# **제 1 장. 프로젝트 개요 및 협업 거버넌스**

## **1.1 개요**

본 설계서는 '산준모(산업안전기사를 준비하는 모임)' 네이버 카페의 47만 수험생 회원 트래픽을 독점적으로 수집·전환시켜 엘캠퍼스 B2C 온라인 플랫폼의 직접 결제 매출로 성공시키기 위한 플랫폼 구축 상세 기능 설계서이다. 가로형(Landscape) 레이아웃 전면 도입을 통해 입력/출력 데이터 칼럼의 가독성을 극대화하였으며, 기존의 기획서 공수 낭비를 걷어내고 디자인, 퍼블리싱, 백엔드 개발이 즉각 동시에 착수될 수 있는 정교한 스펙을 명세한다.

## **1.2 B2C 최적화 린(Lean) 프로덕트 수명 주기 (Product Life Cycle)**

우리는 '상세 통합 설계서(본 문서)'의 정보 밀도가 완벽에 가깝게 촘촘하므로, 표준 포맷의 UI 화면 등은 별도 스토리보드나 기획 장수를 그리는 단계를 과감히 \[선택\]적으로 생략한다. 단, 비즈니스의 시각적 브랜드 가치를 수립하는 \[디자인\]과 모바일 반응형 100% 마크업 및 GA4 스크립팅을 진행하는 \[퍼블리싱\]은 후행 개발 구현을 위한 필수(\[필수\]) 빌드 단계로 지정한다.  
▶ 라이프사이클 순서: PRD 수립 ➔ IA 정의 ➔ WBS 공표 ➔ 상세 통합 설계서 (본 단계) ➔ \[선택\] 화면설계서 ➔ \[필수\] 디자인/퍼블 ➔ \[필수\] 개발 구현

# **제 2 장. 공통 알림 메시지 발송 체계**

## **2.1 개요**

B2C 플랫폼의 주요 사용자 시퀀스 발생 시, 메시지 대기열(Queue) 데몬 서버를 가동하여 회원의 휴대전화로 카카오 알림톡(LMS 우선), SMS, 이메일을 동적 치환 발송함으로써 수험생의 이탈을 막고 고객센터(CS) 운영 효율을 제어한다. 모든 알림톡, SMS, 이메일 발송은 네이버 클라우드 플랫폼의 SENS(Simple & Easy Notification Service) API를 연동하여 처리한다. 카카오 알림톡의 경우, 사전에 네이버 클라우드 플랫폼 SENS 관리 사이트에 접속하여 승인을 획득한 템플릿에 한해서만 발송이 가능하다. 자체 데이터베이스 내의 message\_template 테이블에 메시지 템플릿을 등록해 두고, 발송 트리거 발생 시 SENS API를 통해 실시간으로 발송하는 설계를 채택한다.

## **2.2 알림 메시지 트리거 및 데이터 치환 상세 규격**

런칭 시점에 필수 발송되어야 하는 3대 이벤트에 대한 상세 트리거 시점 및 DB 데이터 치환 명세는 다음과 같다. 모든 발송 이벤트는 네이버 클라우드 SENS API 규격을 준수하며, 알림톡 발송 실패 시(예: 카카오톡 미사용자 또는 수신 차단 상태) SMS/LMS로 자동 전환 발송(Fallback)되는 연동 로직을 기본 탑재한다. 이후 동선은 운영 중 지속적인 스펙 제어를 통해 추가 템플릿을 확장한다.

# **제 3 장. 4대 수직 릴리즈 세트별 상세 데이터 및 기능 설계서**

본 장은 4대 수직 릴리즈 세트에 따라 사용자 프론트 화면(User IA v2.0.0)과 백오피스 어드민(Admin IA v2.0.0) 간의 데이터 이동 및 비즈니스 정책을 1:1로 매핑하여 명세화한 코어 설계 영역이다. 실무 기획서 및 와이어프레임 작성이 간소화되더라도 본 표의 필드값과 정책에 입각하여 퍼블리싱 마크업과 Laravel 백엔드 데이터베이스 스키마 생성이 동시 즉각 착수될 수 있도록 하였다.

# **제 4 장. v2 개정 명세 — PO 피드백 반영**

**본 장은 PO 실무 답변 178건을 기준선으로 삼아 제 1\~3 장의 명세를 개정한 것이다. 제 1\~3 장의 서술과 본 장의 서술이 충돌하면 본 장이 우선한다. 반영일 2026-08-26, 문서 버전 Ver. 2.0.0.**

## **4.1 최우선 확인 사항 — 착수 전 PO 확정 필요**

1\) 메시지 템플릿 미확정 — 알림톡은 카카오 사전 심사에 영업일 1\~3일이 걸린다. 템플릿 목록 확정과 심사 착수를 즉시 진행하지 않으면 오픈 시점에 가입·결제·배송 알림이 통째로 발송되지 않는다.

## **4.2 제 2 장(공통 알림 메시지 발송 체계) 교체 문장**

메시지 템플릿(메일·SMS·알림톡)의 종류·트리거·본문은 본 설계서에서 확정하지 않는다. PO 지시에 따라 메시지 템플릿은 별도 설계 문서에서 진행하며, 화면설계서에는 필요 예상 리스트를 별도 메뉴(ADMN-CONF-007 메시지 템플릿 목록)로 제안한다. 제 2 장의 3대 이벤트 규격은 그 별도 설계가 확정될 때까지의 잠정 명세다.

알림톡은 네이버 클라우드 SENS 관리 콘솔에서 카카오 사전 심사(영업일 1\~3일)를 통과한 템플릿만 발송할 수 있다. 오픈 시점에 1차 필수 템플릿이 미승인 상태면 회원가입 완료·결제 완료·배송 출고 알림이 통째로 나가지 않는다. 목록에 검수 상태 컬럼(`초안 DRAFT` / `검수 대기 PENDING` / `승인 완료 APPROVED` / `검수 반려 REJECTED`)을 두고 미승인 템플릿은 알림톡 발송을 차단한다. 특히 알림톡 템플릿을 신규 등록하거나 기존 승인된 템플릿의 본문·변수를 수정하여 저장할 때는 즉시 승인 상태로 변경되지 않으며, 저장 시 **'카카오 재검수(영업일 1~3일 소요) 요청 안내 및 검수 기간 중 발송 제한/LMS 대체발송 경고 모달'**을 노출한 뒤 상태를 **`검수 대기(PENDING)`**로 전환한다(반면 문자 SMS/LMS 및 이메일 HTML 템플릿은 외부 검수 없이 저장 즉시 활성화된다).

모든 발송 이벤트는 네이버 클라우드 SENS API 규격을 준수한다. 회원가입 완료 시 웰컴 5,000P 및 10% 쿠폰 발급 결과를 치환 변수로 담아 알림톡을 전송한다. 광고성 메시지는 users.is\_marketing\_agreed \= 1 인 회원에게만 발송하며, 거래성 메시지는 수신 동의 여부와 무관하게 발송한다. 알림톡 발송 실패 시 LMS 자동 대체를 허용하되 일일 한도를 설정값으로 두고, 한도 초과 건은 '알림톡 실패' 로 남겨 수동 재발송한다.

1차 필수 트리거 10종 — 회원가입 완료(혜택 지급), 회원가입 완료(재가입·미지급), 결제 완료, 예약대기 등록, 배송 출고, 환불 완료, 환급 심사 결과, 포인트 소멸 예정, 휴면 사전 통지, 1:1 문의 답변.

2차 트리거 6종 — 쿠폰 만료 예정, 계정 잠금, 비밀번호 변경, 소셜 연동, 재고 소진 운영자 알림, 이벤트 발송. 제 2 장 표 안의 '마일리지' 표기는 전량 '포인트' 로 치환한다.

## **4.3 제 3.1 절 \[Set 1\] 회원 인증 — 교체 문장**

아이디 찾기의 1차 조회 키는 DI(중복가입확인정보)로 확정한다. 실명·휴대폰 문자열 크로스 대조는 보조 수단으로만 쓴다. (피드백 23\)

본인인증 발송 횟수 제한은 Config 관리값으로 분리한다. 일일 한도·IP 한도를 config.auth\_send\_cap\_per\_day · auth\_send\_cap\_per\_ip 로 두고, 하드캡 리셋 기준 시각은 00:00 KST 로 한다. (피드백 24·28)

소셜 가입에도 약관 동의 단계를 신설한다. 이메일 가입과 동일 컴포넌트를 재사용하며 본인인증 단계 앞에 배치한다. 현재 설계에는 약관 노드가 없어 설계 누락이다. (피드백 45\)

소셜 가입도 가입 완료 화면(USER-JOIN-003)을 반드시 경유한 뒤 메인으로 이동한다. redirect 파라미터가 있으면 완료 화면의 버튼 문구를 진입 경로에 맞게 치환한다. (피드백 46·79)

네이버 카페 ID 는 이메일 형식(@) 검사를 하지 않는 일반 텍스트로 수집한다. 항목 명칭은 'ID' 로 통일하고 '닉네임' 표기를 섞지 않는다. (피드백 36\)

만 14세 미만 차단 로직은 두지 않는다. 수험생 대상 서비스로 해당 사례가 발생하지 않는다. (피드백 39\)

마케팅 수신 동의는 SMS/이메일로 나누지 않고 users.is\_marketing\_agreed 단일 필드로 수집한다. (피드백 44·172)

보유 자격증 등 선택 항목은 공통코드로 관리하며 코드값은 자동 생성한다. 화면에서 코드를 직접 입력받지 않는다. (피드백 42·172)

계정 잠금 상태와 회원 상태를 하나의 값으로 합치지 않는다. users 테이블에 is\_locked(자동 5회 오입력 잠금)와 member\_status(정상/휴면/정지)를 각각 두고, lock\_reason 에 auto\_5fail / admin\_block 을 구분 저장한다. 한 값으로 합치면 관리자가 정지시킨 회원이 비밀번호 재설정만으로 정지를 해제하는 결함이 발생한다. (피드백 25\)

로그인 실패 문구는 아이디 오류·비밀번호 오류를 구분하지 않고 통합 문구 하나로 노출한다. 계정 존재 여부가 노출되지 않도록 한다.

비밀번호 해시는 bcrypt 또는 Argon2 를 사용한다. SHA-256 단독은 부적합하므로 설계서·프로세스맵의 SHA-256 표기를 모두 대체한다. (피드백 31\)

휴면 전환 기준은 최종 로그인 후 1년 미접속이다. 사전 통지를 발송하고, 휴면 회원이 로그인하면 해제를 강제한다. 해제 전에는 어떤 메뉴로도 진입할 수 없다. (피드백 29·75)

비밀번호 재설정 시 재인증은 생략한다. 조합 규칙 위배로 입력창을 초기화하는 동작은 서버 검증 실패일 때만 수행하며, 실시간 검증에서는 초기화하지 않는다. (피드백 30·32·33)

소셜 전용 회원의 비밀번호 설정은 가입 단계가 아니라 마이페이지 회원정보 수정에서 제공한다. (피드백 34\)

가입 완료 즉시 웰컴 5,000P 및 10% 쿠폰을 자동 발급하고 SENS API 로 알림톡을 전송한다. 재가입 회원에게는 지급하지 않으며 미지급 사유를 안내한다.

## **4.4 제 3.2 절 \[Set 2\] 강사 홈 및 동영상 수강 엔진**

'전용관' 이라는 신규 용어를 사용하지 않는다. 문서·화면·코드 전반의 표기를 '강사 홈' 으로 통일한다. (피드백 15·47)

강사 홈의 교안·기출 PDF 자료실은 제공하지 않는다. 강사 홈은 맛보기 영상만 제공한다. PDF DRM·워터마크는 기능 미보유로 판단 후 결정한다. (피드백 48·118·132)

GNB '강사소개' 진입 시 랜딩 대상 강사는 하드코딩하지 않고 ADMN-PROD-006 의 노출순서 1번을 따른다. 강사 수 확장에 대응할 수 있도록 강사 홈은 공용 템플릿으로 구성한다. (피드백 113·114·115)

숨김 처리된 강사의 홈 URL 로 진입하면 활성 강사 홈으로 302 리다이렉트한다. 2차에 강사 목록 화면(USER-INST-000)을 신설해 그쪽으로 전환한다. (피드백 114\)

강사 홈에 학습 Q\&A 진입점을 신설한다. 레이어 목록(USER-QNA-001)과 질문 작성(USER-QNA-002)으로 구성하며 작성 권한은 해당 강사의 유료 수강생으로 한정한다. 문의는 board\_qna.instructor\_id 로 강사별 구분한다. (피드백 99\)

모바일 크롬·사파리 재생은 커스텀 URI 스키마(starplayer://)로 플레이어 앱을 자동 기동한다. 브라우저 재생 폴백 경로는 삭제하고, 앱 미설치 시 스토어 유도로 단일화한다. (피드백 129\)

백그라운드 브라우저 사망에 대비해 HttpOnly Cookie 기반 Silent Refresh 로 세션을 자동 복구한다. 진도 정합성은 플레이어 앱이 당사 백엔드로 직접 보내는 Direct Server Callback 으로 사수하며, 브라우저 경유 갱신에 의존하지 않는다.

수강 완료 판정 진도 기준은 90% 다. (피드백 128\)

차수 순차 잠금은 적용하지 않는다. 수강생은 임의 차수를 먼저 재생할 수 있다. (피드백 131\)

이어보기 퀵 위젯은 최근 재생 중단된 강좌·차수·재생초를 DB 에서 조회해 내 강의실 대시보드(USER-MY-001) 최상단에 로드한다. 클릭 시 플레이어로 직행하지 않고 내 강의실을 경유해 재생하며, 모바일에서는 위젯을 노출하지 않는다. 재생 불가 상태면 위젯을 숨긴다. (피드백 13·124·125)

부정 사용 판정은 파트너사(엑시스소프트) 로그를 활용하고 자체 적재는 하지 않는다. 어드민에는 정지 기능만 신설하며 임계치 자동 필터는 2차로 이관한다. 재생 수단은 lecture.player\_type(starplayer / youtube / html5)으로 상품별 택일한다. 수강 기간은 상품별 레코드로 관리하고 기산점은 결제 승인일이다. (피드백 71·74·111·122·123·127)

## **4.5 제 3.3 절 \[Set 3\] 복합 주문/배송**

연동 PG사 및 지원 결제수단 범위는 [표 5.1-A] 마스터 기준표를 따른다. 4.1 의 1\) 확정 전까지는 잠정이다. (피드백 160·161)

모든 상품이 면세이므로 사용자 화면·메일 본문 어디에도 면세 태그와 면세 안내 문구를 노출하지 않는다. PG 전문의 Tax-Exempt 처리는 백엔드에 그대로 유지한다. (피드백 136·141·142)

패키지 상품 진입 시 강좌와 교재를 개별 독립 라인 아이템(order\_items)으로 분할 인서트한다. 교재 라인은 다른 상품과 동일하게 삭제·선택 해제할 수 있으며, 교재 전용 삭제 버튼·전용 안내 문구·전용 확인 팝업을 두지 않는다. 교재 라인이 사라지면 배송지 입력 폼이 비활성화되고 배송비만 재계산된다. (피드백 133·134·138)

실물 교재가 포함된 주문에서만 배송지 입력 폼을 동적으로 활성화한다. 주소 입력은 카카오 우편번호 서비스를 사용한다. (피드백 139\)

도서정가제 준수를 위해 교재비 상당액에는 쿠폰·포인트 할인을 원천 차단하고 오직 강좌 금액에서만 공제한다. 고지는 전 화면 공통 범용 문구 1개만 사용하며, 상품별 금액을 대입한 계산 안내와 '계산 예시 보기' 토글은 삭제한다. 노출 위치는 패키지 상세 1곳, 주문서 1곳으로 한정한다. (피드백 55·56·155)

고정 고지 문구 — "출판문화산업 진흥법에 따라 교재에는 할인·적립이 적용되지 않으며, 보유하신 쿠폰과 포인트는 강좌 금액 한도 내에서만 사용됩니다."

무료배송 판정 기준은 교재 라인 합계 30,000원이다. (피드백 85·145)

쿠폰은 1회 결제 시 1매만 사용할 수 있으며 1매는 1상품에만 적용한다. 특정 상품 전용 쿠폰은 상품별로 1매씩 사용할 수 있고, 전체 상품·카테고리 적용 쿠폰은 특정 상품 전용 쿠폰과 중복 사용할 수 없어 사용자가 택일한다. 쿠폰 최소 결제금액의 판정 기준액은 쿠폰 적용 전, 교재 라인 제외, 배송비 제외한 강좌 라인 합계다. 포인트는 최소 1,000P 부터 사용할 수 있다. 관리자가 상품 등록 시 쿠폰·포인트 사용 불가 제약을 걸지 않았다면 쿠폰과 포인트를 동시에 사용할 수 있다. (피드백 146·147)

orders.order\_no 는 YYYYMMDD \+ 구분자 1자리 \+ 일련번호 7자리로 생성한다. 구분자는 주문에 포함된 상품 유형 구성으로 결정한다. 교재·강좌·패키지가 모두 있으면 A, 패키지가 없고 강좌가 포함되면 L, 패키지가 포함되면 P, 강좌·패키지 없이 교재만 있으면 B 를 부여한다. 어드민 주문 검색은 이 구분자를 조건으로 지원한다. (피드백 154\)

예약 판매 — book.is\_preorder(TINYINT)와 book.release\_date(DATE)를 신설한다. is\_preorder \= True 인 상품의 결제 건은 order\_items.line\_status 를 preorder\_hold(예약대기)로 적재한다. ADMN-ORD-002 3PL 발주 엑셀 추출 쿼리는 line\_status \<\> 'preorder\_hold' 조건을 강제로 포함하며, 다운로드 요약에 "총 N건 중 발주 대상 M건 / 예약대기 제외 K건" 을 표기한다. preorder\_hold 상태에서 사용자가 취소를 요청하면 어드민 승인 없이 PG 취소 API 를 즉시 호출해 100% 자동 환불한다. (피드백 90\)

인강 라인의 수량 개념을 삭제한다. 인강은 1개 고정이며 수량은 교재 라인에만 재고 범위 내에서 존재한다. cart\_items·order\_items 의 qty 는 교재 라인에서만 의미를 갖는다. (피드백 121·151)

찜하기 기능은 전면 삭제한다. wishlist 테이블과 관련 UI 를 두지 않는다. (피드백 91\)

상품 목록·상세의 '할인 불가' 태그를 삭제하고 정가·판매가 표기 규칙을 통일한다. 재고 0 인 교재는 판매를 중단하며, 재고 0 교재가 포함된 패키지도 함께 중단한다. (피드백 62·64·69·123·135·137)

장바구니 담기와 주문은 로그인을 필수로 한다. 비로그인 상태에서 담은 장바구니는 로그인 후에도 유지한다. (피드백 150\)

환급 지급은 원결제 건에 대한 PG 취소를 1순위로 시도한다. 다만 카드사·PG 의 취소 가능 기간(통상 결제일 기준 90일)을 초과하면 취소 API 가 실패하므로 아래 6개 규격을 강제한다.

(1) 선행 수집 — 사용자 신청 폼(USER-MY-011)에서 환급용 무통장 계좌(은행 코드·계좌번호), 예금주 정보, 통장 사본 파일 업로드를 필수로 수집한다. 계좌번호와 예금주는 refund\_request.account\_no\_enc · account\_holder\_enc 에 양방향 암호화로 저장하고 화면에서는 마스킹한다.

(2) 라우팅 판정 — 지급 실행 시 DATEDIFF(NOW(), payment.approved\_at) 이 90 을 초과하면 PG 취소를 시도하지 않고 곧바로 refund\_request.payout\_method \= 'bank\_transfer\_wait'(무통장 이체 대기)로 적재한다.

(3) 폴백 전환 — 90일 이내라도 PG 취소 API 가 실패 응답을 반환하면 재시도 없이 즉시 bank\_transfer\_wait 로 전환하고, 실패 응답 코드·메시지를 refund\_request.pg\_fail\_log 에 남긴다.

(4) 지급 실행 — bank\_transfer\_wait 건은 펌뱅킹 엑셀 다운로드(은행·계좌·예금주·금액·적요)로 일괄 추출해 은행 대량이체로 처리한다. 이 다운로드는 사유 입력 대상이며 admin\_audit\_logs 에 적재한다.

(5) 권한 분리 — 심사 롤과 지급 확정 롤을 분리한다. 동일 관리자가 승인과 실지급을 모두 처리할 수 없다. (6) 계좌 검증 — 계좌 실명조회 API 는 1차에 도입하지 않는다. 예금주 불일치로 이체가 반송되는 건은 CS 가 처리한다.

환급 심사 결과는 게시판형 답글로 사용자에게 전달한다. 반려 시 답글은 필수다. 차감액은 올림, 환불액은 내림으로 연산한다. 배송완료 D+7 이 지난 건은 반품 신청 버튼을 비활성화하며 금액 수동 보정칸은 두지 않는다. (피드백 164·166·168)

다중 강사 정산 — 동일 상품에 다중 강사 배정 시 개별 지분율 총합이 100.00% 를 만족해야 저장이 가동되는 시스템 락을 둔다. 계약 만료일과 전시 기간의 교집합 검증을 동시에 수행한다. 매출 마감 확정 즉시 DB 레코드에 Locked=True 속성을 부여해 수정·삭제를 차단한다. 마이너스 포인트를 지닌 부채 회원은 탈퇴를 Lock 하고 ADMN-USER-004 어드민 예외 승인으로만 해제한다. (피드백 173\)

**강좌 · 교재 · 패키지 · 강사 프로필 · 강의는 목록 화면과 등록 · 수정 화면(ADMN-PROD-002-S1 · 003-S2 · 004-S1 · 005-S1 · 006-S1)을 분리한다(v4 · v9). 커리큘럼 구성은 ADMN-PROD-003-S1 이다.**

**패키지 등록에 환급 대상 체크 \+ 인정 진도율 입력을 둔다. 판매 이력이 있는 패키지도 구성을 바꿀 수 있으며 기존 구매자에게도 적용하되 수강 기간은 바꾸지 않고 정산 배분은 다음 정산부터 적용한다. 강좌를 빼도 기존 구매자 수강권은 유지한다(v8 · v12).**

## **5.8 \[Set 4\] 권리자 계약 · 정산 — 합의서 v3.8.3**

**정산 · 계약의 기준 문서는 「산준모 정산 및 계약 기획 합의서 v3.8.3」이며 설계서와 충돌하면 합의서를 따른다(v8 · v11).**

**화면 체계 — 권리자 계약 원장(ADMN-INST-001 · S1 · S2 · P1), 약정금 마일스톤 검수 및 승인 원장(ADMN-INST-002), 상품별 권리자 매핑(ADMN-SETT-001 · S1 · P1), 월간 정산 및 집행(ADMN-SETT-002 · S1 · S2), PG 정산 원장 대사(ADMN-SETT-004 · S1), 정산 수동 조정(ADMN-SETT-005 · S1), 합격 환급반 관리(ADMN-SETT-006), 수취인 분할 지분 설정(ADMN-SETT-007 · S1), 사업자등록 확인 이력(ADMN-SETT-008), 내부 정산 조회(ADMN-SETT-009), 물류비 대사(ADMN-SETT-011 · S1). ADMN-SETT-003 은 결번이다(v7 · v9).**

**정산액은 5개 트랙(Track A 강의 R/S · B-1 자사 발행 인세 · B-2 위탁 판매 · G 일반 소비재 · S 라인 지원금)을 11단계 통합 연산 엔진(CARRY\_IN → ACCRUAL → MMG\_ADJ → DEDUCT → SUPPORT\_CAP → PREPAY\_OFFSET → LUMPSUM\_ADD → PAYEE\_SPLIT → TAX → CLAIM → PAYOUT)에 이 순서대로만 통과시켜 산출한다. 중간 연산은 DECIMAL(18,4)로 보존하고 원단위 절사는 권리자별 · 라인별 월 합산 직후 1회(Floor)만 한다.**

**세무 처리는 세무 판정 매트릭스(TX-01\~TX-13)로 판정한다. 원천징수는 소득세 → 지방소득세 순차 2단 절사이며 합산세율을 직접 곱하지 않는다. 일반 소비재는 TX-13(부가가치세 10% 별도)이다.**

**마감 순서는 PG 정산 원장 대사 → 월간 정산 마감 → 펌뱅킹 지급 → 송금 증빙 바인딩이다. 마감(Lock) 해제 기능은 없으며 마감 후 오류는 차월 정산 수동 조정 라인(원 발생월 / 반영월)으로 바로잡는다. 미매핑 거래가 있으면 마감할 수 없다(v9). PG 명세는 엑셀 수기 업로드로 수집한다(v11).**

**재무 책임자를 두지 않고 재무 담당자 한 단계로 운영한다. 2단계 승인 절차는 전부 삭제하며 수동 조정은 소명 20자 이상을 남기고 단독 확정한다(v8).**

**계약 — 정산에 적용된 요율 · 개시일은 Lock, 만료일은 과거로 당길 수 없다. 중도해지일 기준으로 종료하고 기 발생 정산은 지급을 유지한다. 자동 연장은 1년 단위 날짜 기반 전이(승인 없음)이며 만료 예고 알림(D-30 · D-14 · D-7)은 2차 구현이다. 계약 상세는 계약 박스 구조로 재설계한다. 상품별 권리자 매핑은 적용 계약 선택이 필수다(v6 · v8).**

**개발지원금은 한도형(CAPPED) 외에 무한도형(UNLIMITED)을 두며 무한도형은 종료 정책 NONE 으로 고정한다. 전속계약금 위약 조항은 기록만 하고 정산 엔진에 넣지 않으며 위약금은 별도 원장에서 관리한다(v11).**

**지급일은 매월 10일이며 계산서는 지급일 5일 전까지 권장한다. 국세청 사업자 확인은 유효기간 90일이며 경과 권리자는 정산 시 일괄 재조회한다. 월간 정산 조회는 월 선택(month picker) 방식이다(v9).**
