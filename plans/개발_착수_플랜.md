# 산준모닷컴 1인 개발 가능성 검증 — 개발 착수 플랜

> 작성 2026-10-22 · 수정 2026-10-23 (외부 연동 어댑터 · 가짜 구현 방식) · 상태: **검토 중 (진행 여부 미결정)** · 작성 Claude Code · 검토 white(김영호)
>
> 이 문서는 "white + Claude Code가 로컬에서 A to Z 구현이 가능한가"를 가늠하기 위한 계획이다. 개발팀의 진행과는 별개다.
> 1차에서는 외부 연동을 실제로 붙이지 않으므로 키 · 시크릿이 필요 없다. 실연동 단계(3-8)에서 받는 비밀 값은 이 문서에 적지 않고 `plans/개발_자료.local.md`(로컬 전용, 저장소 · 드라이브에 올라가지 않음)에 적은 뒤 `.env`로 옮긴다.

---

## 1. 목적과 범위

| 항목 | 내용 |
| :--- | :--- |
| 목적 | 통합설계서 · 정산 00~04권 · 백오피스 프로토타입을 기준으로 1인 개발(A to Z)이 가능한지 실제로 만들어 보며 판단한다. |
| 범위 | 백오피스 전체(SNB 45개 메뉴) + 사용자 프론트(퍼블리싱 PHP 제공분) + 정산 엔진(1~11단계) + 엑셀로 처리하는 업무(대량이체 · 홈택스 대사 · PG 정산 대사 · 3PL) |
| 외부 연동 | **어댑터 + 가짜 구현으로 둔다.** 본인인증 · 소셜 로그인 · 결제 · VOD DRM · SENS · 국세청은 인터페이스와 가짜 구현만 만들고 흐름이 끝까지 돌아가게 한다. 실연동은 1차 이후(3-8) |
| 개발 장소 | 로컬 PC `D:\Work\` 아래 새 폴더. C 드라이브는 쓰지 않는다. |
| 1차 제외 | 외부 연동 실연동(위 6종) / 펌뱅킹(은행 API) — 대량이체 엑셀로 대신 / 전자세금계산서 발행 대행 · 국세청 직접 연동 / 운영 서버 구성(코드로만 준비) / KMS 실연동 |
| 판단 시점 | 7절 진행 판단 기준 |

| 엑셀 | maatwebsite/excel 4.x (PhpSpreadsheet 5.x) | 3.x는 PHP 8.5 설치 불가 문제가 있었고 4.0(2026-08)에서 해결. 3-2 첫 검증 대상(문제 시 OpenSpout) |

| 저장소 | 새 GitHub 저장소 + `D:\Work\` 아래 폴더 | 설계 저장소와 분리. 드라이브 자동 동기화 대상 아님. `.env` 커밋 금지 |
| **외부 연동 방식** | **어댑터(인터페이스) + 가짜 구현 / 실연동 구현** | `.env`의 드라이버 값으로 전환(예: `PAYMENT_DRIVER=fake` → `toss`). 가짜 구현은 임의의 키 · 식별자(CI/DI, 결제 키, 승인번호, 사용자 고유 ID 등)를 만들어 돌려주고 성공 · 실패 · 예외 상태를 재현한다. **주고받는 데이터 모양은 정본 문서와 업체 공개 API 문서를 기준으로 지금 정한다**(테이블 구조와 대사 로직이 여기에 묶이므로). 어댑터마다 "실연동 시 확인 항목"을 남긴다 |
| 세금계산서 · 계산서 | **권리자 발행 · 제출 + 홈택스 엑셀 대사** | 역발행(발행 대행) 미사용. 권리자 제출 기본 + 운영자 대리 등록. 미제출은 지급 보류 사유 아님. 정본 반영 완료(v6.28, 제2권 제9장) |
| 지급 이체 | **은행 대량이체 엑셀 + 결과 파일 대사** (실제 구현) | 펌뱅킹은 2차. 정본 반영 완료(v6.28) |
| 메시지 | 네이버 클라우드 SENS (알림톡 · SMS · MAIL) — 1차는 가짜 | 가짜 구현은 실제 발송 없이 발송 이력(CONF-007)에 기록한다. SENS는 콘솔에 등록된 템플릿을 조회 API로 불러오는 구조이므로, 조회 응답과 같은 모양의 **더미 템플릿 목록**(템플릿 코드 · 문구 · 검수 상태 · 반려 사유)을 두고 백오피스(CONF-004)의 코드 연결 · 상태 동기화 · 승인 템플릿만 발송을 그대로 동작시킨다 |
| 휴대폰 본인인증 | KG이니시스 — 1차는 가짜 | 입력값으로 CI/DI를 만들어 반환, 인증 실패 · 중복 가입(DI 일치) 재현 |
| 소셜 로그인 | 카카오 · 네이버 (· 구글) — 1차는 가짜 | 임의 고유 ID · 이메일 반환, 연동 해제 · 마지막 로그인 수단 보호 로직은 실제 구현 |
| 결제 | 토스페이먼츠 — 1차는 가짜 | 승인 · 전체 취소 · 부분 취소 · 실패, 가상계좌 입금 대기 → 입금 완료(웹훅은 내부 호출로 흉내). 결제 키 · 승인번호는 임의 생성 |
| VOD DRM | 업체 SDK — 1차는 가짜 | 일반 동영상 재생으로 대신. 이어보기 · 진도율 · 동시 접속 제한은 우리 쪽 로직이라 실제 구현 |
| 국세청 | 공공데이터포털 사업자 상태조회 — 1차는 가짜 | 사업자번호별로 정해진 상태(계속 · 휴업 · 폐업, 과세유형)를 반환 |
| 3PL | 출고지시 · 송장 엑셀 (실제 구현) | 물류 대행사 미팅 후 양식 확정 |

## 4. 정합성 검증 방식

| 대상 | 방법 |
| :--- | :--- |
| 문서 규칙 ↔ 코드 | 규칙 번호 대조표로 단계마다 누락 0 확인 |
| 금액 계산 | 정산 04권 케이스를 자동 테스트로 |
| 화면 | 프로토타입 ↔ 실제 화면을 Playwright로 비교(목록 항목 · 버튼 · 검증 메시지) |
| 데이터 | 프로토타입 기준정보 · 샘플 데이터를 시드로 옮기고 화면 간 데이터 대조 도구 재사용 |
| 어댑터 | 같은 테스트를 가짜 · 실연동 드라이버에 모두 돌릴 수 있게 작성(실연동 시 재사용) |
| 사람이 확인할 영역 | 세무 · 법무 판단, 보안 점검, 실연동 단계의 실제 결제 · 은행 · DRM 동작 |

## 6. 위험과 대응

| 위험 | 대응 |
| :--- | :--- |
| 엑셀 라이브러리의 PHP 8.5 호환 | 3-2 첫 검증 항목. 문제 시 OpenSpout로 대체 |
| 가짜 구현이 실제 연동과 다르게 동작 | 데이터 모양은 공개 API 문서 기준으로 정하고, 어댑터마다 "실연동 시 확인 항목"을 기록. 같은 테스트를 실연동 드라이버에 다시 돌린다 |
| 엑셀 양식이 실제와 다름 | 실제 양식 · 샘플(5절 A 4~7번)을 받아 만든다. 못 받은 양식은 열 매핑을 설정으로 빼 둔다 |
| 세션이 바뀌어도 일관성 유지 | 새 저장소에 작업 규칙 · 진행 상태 문서 · 규칙 대조표를 처음부터 둔다 |
| 규모가 큼(백오피스 59개 기본 화면 + 보조 화면 + 프론트 + 정산) | 단계별 완료 기준으로 끊고 단계마다 white 확인 |
| 정본 문서 해석 차이 | 개발 기준 정본 안내 + 해석 질문 목록 운영 |
| 사람 검토가 꼭 필요한 영역 | 세무 · 법무, 보안, 실연동 단계의 실제 결제 · 은행 · DRM은 테스트 통과와 별개로 확인 |
